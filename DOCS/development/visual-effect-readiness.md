# 시각 효과 적용을 전제로 한 표시 요소 설계

사용자에게 보이는 모든 표시 요소는 나중에 시각 효과가 적용될 수 있다고 기본적으로 가정하고 설계합니다. 이 문서는 uGUI 요소, 2D 이미지 오브젝트, 3D 모델, RenderTexture로 UI에 표시되는 3D 화면, 배경, 아이콘, 텍스트, 테두리처럼 화면에 나타나는 요소를 만들거나 수정할 때 따르는 공통 규칙입니다. 특정 효과를 이번 작업에서 구현하라는 뜻은 아니며, 효과를 나중에 추가해도 레이아웃·가독성·입력·물리·데이터가 깨지지 않도록 구조를 준비하라는 뜻입니다.

프로젝트는 URP(`com.unity.render-pipelines.universal`)를 사용합니다. 아래 렌더링 관련 규칙은 URP 기준입니다.

## 고려해야 하는 효과 범주

| 범주 | 예시 | 주로 영향을 받는 것 |
| --- | --- | --- |
| 화면 왜곡 | 글리치, 노이즈, 모자이크, 색수차, 스캔라인, 디졸브 | 셰이더·Material, 렌더 범위, 가독성 |
| 형태·마스크 | 절차적 도형 셰이더, 둥근 모서리, 잘린 모서리, 마스크, 컷아웃, 정점 변형 | 실제 보이는 외곽과 입력·충돌 영역의 차이 |
| 테두리·강조 | border, outline, glow, 림 라이트, 그림자, 포커스 표시, 선택 프레임 | 요소 바깥으로 확장되는 그리기 영역, 텍스트 위 겹침 |
| Transform 연출 | 흔들림, 확대·축소, 회전, 박동, 등장·퇴장 | 레이아웃·배치 계산, 물리, 인접 요소와의 충돌 |
| 색·투명도 | 페이드, 점멸, 색조 변경, 피격 플래시 | 상태 전달, 대비, 접근성, 투명 정렬 |
| 전경·배경 오버레이 | 파티클, 화면 전환, 배경 효과 레이어, 후처리 | 그리기 순서, 입력 차단, 적용 범위 |

## 공통 규칙

다음 규칙은 표시 방식과 관계없이 적용합니다.

- 배치를 결정하는 Transform과 효과가 변형하는 표시 Transform을 분리합니다. 레이아웃 시스템, 배치 코드, 물리 시뮬레이션이 쓰는 Transform에는 Animator나 효과 코드가 위치·크기·회전을 기록하지 않습니다.
- 배경, 내용물, 테두리, 텍스트, 전경 효과처럼 독립적으로 효과를 받을 수 있는 대상은 별도 표시 루트로 구분합니다. 하나의 Graphic이나 Renderer에 모든 역할을 합치지 않습니다.
- 정렬·크기·배치 계산은 효과 적용 전 기준을 사용합니다. 효과로 늘어난 그리기 범위, 투명 여백, outline, 흔들리는 위치를 기준으로 사용하지 않습니다. 표시 방식별 기준은 아래 절에서 정합니다.
- 효과는 의미가 있는 Transform 값을 덮어쓰지 않습니다. 결과 면 보정처럼 게임 의미가 있는 회전이나 위치가 있으면 효과는 그보다 아래 자식에 적용하거나 기존 값에 더하는 방식으로 적용합니다.
- 보이는 외곽이 효과로 바뀌어도 입력 영역과 충돌 영역은 의도한 크기와 형태를 유지합니다. 효과 전용 오버레이와 전경 레이어는 기본적으로 입력을 차단하지 않습니다.

## Material과 상태 관리

- 효과 구현은 공유 Material 에셋 자체를 변경하지 않습니다. `Renderer.sharedMaterial`이나 공유 UI Material의 속성을 실행 중에 바꾸지 않습니다.
- 개별 값 변경은 다음 중에서 고르고, 선택한 방식을 해당 기능 문서에 적습니다.
  - URP에서 `MaterialPropertyBlock`을 사용하면 해당 Renderer는 SRP Batcher가 적용되지 않습니다. 화면에 소수만 있는 오브젝트나 짧은 효과에 사용합니다.
  - 많은 오브젝트가 같은 효과를 받으면 수명이 관리되는 Material 인스턴스나 효과 전용 Material 교체를 사용합니다. 생성한 Material 인스턴스는 소유자가 파괴합니다.
  - uGUI Graphic은 `Graphic.material` 교체나 `IMaterialModifier`로 인스턴스를 적용하고 원래 Material로 되돌릴 수 있어야 합니다.
- 효과는 켜기·끄기와 등록·해제를 지원하고, 해제·비활성화·파괴 시 변경한 색·알파·Transform·Material·Renderer 상태를 원래대로 복원하거나 정리합니다.
- 여러 효과가 같은 속성을 동시에 바꿀 수 있는 경우 소유권이나 합성 순서를 명시합니다. 나중에 실행된 효과가 이전 효과의 값을 조용히 덮어쓰지 않게 합니다.
- 풀링되거나 재사용되는 표시 요소는 재사용 시 이전 효과 상태가 남지 않도록 초기화합니다.

## uGUI 요소

- 효과 적용 전 기준은 레이아웃이 계산한 RectTransform 영역입니다. LayoutGroup·ContentSizeFitter가 제어하는 루트는 레이아웃 전용으로 둡니다.
- border와 outline은 요소 바깥이나 안쪽으로 그려질 수 있으므로 여백과 인접 요소 간격을 그 두께만큼 확보합니다. Image+`Outline`처럼 면 전체를 복제해 텍스트를 덮는 방식 대신 테두리 전용 Graphic처럼 필요한 영역만 그리는 방식을 우선합니다.
- 모양 셰이더나 마스크로 보이는 외곽이 바뀌어도 Raycast 대상의 크기와 형태는 의도한 터치 대상 크기를 유지합니다. 필요하면 Raycast 대상과 시각 대상을 분리합니다.
- `RectMask2D`와 `Mask`는 자식 효과를 잘라낼 수 있습니다. 스크롤 영역 안의 항목에 바깥으로 넘치는 glow나 outline을 적용할 계획이면 잘림을 허용할지, 여백을 둘지 정합니다.

## 2D 이미지 오브젝트

`SpriteRenderer`처럼 Canvas 밖에서 그리는 2D 오브젝트에 적용합니다. uGUI `Image`에 쓰는 Sprite에도 텍스처 관련 규칙은 같이 적용합니다.

- 효과 적용 전 기준은 루트의 배치 위치와 의도한 표시 크기입니다. Sprite의 투명 여백이나 효과로 늘어난 bounds를 배치 기준으로 사용하지 않습니다. 기준 크기가 Sprite마다 다르면 별도 데이터로 둡니다.
- outline·glow·디졸브처럼 외곽 바깥에 그리는 셰이더 효과를 적용할 수 있는 Sprite는 효과 두께만큼 투명 여백을 텍스처에 둡니다. Sprite 메시가 `Tight`이면 투명 영역이 잘려 바깥 효과가 그려지지 않으므로 이런 Sprite는 `Full Rect`를 사용합니다.
- Sprite Atlas에 넣는 Sprite는 효과가 주변 픽셀을 샘플링하므로 Atlas Padding을 효과 샘플링 거리 이상으로 설정해 다른 Sprite가 번지지 않게 합니다.
- 그리기 순서는 Sorting Layer와 Order in Layer로 명시합니다. 효과 레이어를 대상의 앞이나 뒤에 붙일 때 같은 Sorting Group 안에서 순서를 정하고, 위치의 z 값이나 생성 순서에 의존하지 않습니다.
- 입력이나 충돌에 쓰는 `Collider2D`는 루트나 별도 자식에 두고, 효과를 받는 Sprite 표시 자식과 분리합니다. Sprite 모양에서 자동 생성한 충돌 형태가 효과에 따라 바뀌지 않게 합니다.

## 3D 모델

- 계층은 최소한 배치·물리용 Root와 효과를 받는 Visual로 나눕니다. 게임 의미가 있는 회전 보정이 Visual에 있으면 효과용 자식을 한 단계 더 둡니다.
- 효과 적용 전 기준은 모델 데이터에 정의된 기준값입니다. 예를 들어 정지 높이, 경계 반경, 형태 정의의 크기가 기준이며, 실행 중 `Renderer.bounds`는 효과로 변할 수 있으므로 배치·구도 계산 기준으로 사용하지 않습니다.
- `Rigidbody`와 `Collider`가 있는 오브젝트는 효과가 물리 Transform이나 Collider 크기를 바꾸지 않습니다. 흔들림·확대·정점 변형 셰이더는 시각 메시에만 적용하며 물리 결과와 판정 결과를 바꾸지 않아야 합니다.
- 3D outline은 구현 방식마다 제약이 다르므로 기능 문서에 선택한 방식을 적습니다.
  - 메시를 법선 방향으로 키워 한 번 더 그리는 방식은 하드 엣지 메시에서 외곽선이 끊어질 수 있고, 서브메시·멀티 Material 모델에서는 모든 서브메시를 처리해야 합니다.
  - URP Renderer Feature나 후처리 방식은 카메라·레이어 단위로 동작하므로 대상 오브젝트의 레이어와 해당 카메라의 Renderer 설정을 함께 관리합니다.
- 반투명 효과(페이드, 디졸브)는 불투명 Material을 투명 큐로 바꾸면 그림자, 깊이 쓰기, 정렬 결과가 달라집니다. 페이드가 필요한 모델은 처음부터 이를 지원하는 셰이더나 디더 방식을 고려합니다.
- 효과용 셰이더 키워드를 추가하면 셰이더 변형 수와 빌드 크기가 늘어납니다. 품질 단계에서 끌 수 있게 하고 사용하지 않는 변형은 제거합니다.

## RenderTexture로 UI에 표시되는 3D

별도 Stage의 Camera가 RenderTexture에 그리고 `RawImage`로 UI에 표시하는 화면에 적용합니다.

- 효과를 적용할 위치를 구분합니다.
  - 3D Stage 안의 효과는 모델별 효과입니다. 모델 Visual이나 Stage Camera의 Renderer 설정에서 처리합니다.
  - `RawImage`에 적용하는 효과는 3D 화면 전체에 대한 UI 효과입니다. uGUI 규칙을 따르며 3D 모델 각각을 구분할 수 없습니다.
- RenderTexture 해상도는 효과 품질에 영향을 줍니다. 노이즈·outline 두께는 RenderTexture 픽셀 기준인지 화면 픽셀 기준인지 정하고, 해상도 상한이나 재할당 정책이 바뀌어도 효과 두께가 의도대로 보이게 합니다.
- 구도 계산은 효과 적용 전 기준으로 모델이 화면 안에 들어오게 합니다. 바깥으로 넘치는 glow·outline·흔들림이 RenderTexture 경계에서 잘리지 않도록 구도 여백을 두거나 잘림을 허용할지 정합니다.
- Stage 전용 레이어와 Camera Culling Mask를 유지합니다. 후처리 Volume이나 Renderer Feature 효과는 Stage Camera와 운영 Camera가 서로의 효과를 받지 않게 범위를 분리합니다.
- RenderTexture의 알파를 UI 합성에 사용하면 효과가 알파를 바꿀 때 배경 투명도도 함께 바뀝니다. 투명 배경을 쓰는 Stage에서는 효과가 알파를 어떻게 다루는지 확인합니다.

## 가독성, 접근성과 품질 단계

- 필수 텍스트와 상태 정보는 글리치·노이즈·outline·색 효과가 적용되어도 읽을 수 있어야 합니다. 필요하면 텍스트 뒤에 효과와 독립된 불투명 배경을 둡니다. 3D 모델 위의 라벨이나 면 숫자도 같은 기준을 적용합니다.
- 효과만으로 필수 상태를 전달하지 않습니다. 효과가 꺼지거나 품질 단계가 낮아져도 텍스트·아이콘·도형 등으로 같은 정보를 확인할 수 있어야 합니다.
- 깜박임, 강한 노이즈, 흔들림처럼 불편을 줄 수 있는 효과는 줄이거나 끌 수 있는 경로를 고려합니다.
- 고비용 셰이더·후처리·추가 Renderer 패스는 모바일 성능과 품질 단계를 고려해 선택적으로 비활성화할 수 있어야 합니다. 효과를 끈 상태도 정상적인 표시 상태로 설계합니다.

## 작업 범위 원칙

- 새 표시 요소를 만들 때는 효과가 들어갈 자리를 구조적으로 확보하지만, 요청되지 않은 효과 시스템이나 셰이더 프레임워크를 미리 구현하지 않습니다.
- 기존 요소에 효과를 추가할 때는 배치·레이아웃·물리 Transform을 직접 변형하지 말고 해당 표시 루트를 사용합니다. 표시 루트가 없으면 기존 Prefab 계층과 직렬화 참조를 보존하면서 필요한 루트만 추가합니다.
- 효과를 위해 계층, 직렬화 참조, 레이어, Renderer 설정을 바꾸면 관련 아키텍처 문서를 같은 변경에서 갱신합니다.

`SpriteRenderer` 기반 2D 오브젝트에 이 규칙을 적용한 예는 아직 없습니다. 캐릭터와 적의 3D 표시도 아직 구현되지 않았으므로, 추가할 때 이 문서의 3D와 RenderTexture 규칙을 따릅니다.

## 검증 시 확인 사항

- 효과를 켠 상태와 끈 상태에서 레이아웃 크기, 배치 위치, 3D 구도가 같은지 확인합니다.
- outline·glow·흔들림이 인접 요소나 필수 텍스트를 가리지 않고, Mask·Sprite 메시·RenderTexture 경계에서 의도하지 않게 잘리지 않는지 확인합니다.
- 모양 셰이더나 마스크 적용 후에도 마우스·터치·컨트롤러 입력 대상과 포커스 표시가 의도대로 동작하는지 확인합니다.
- 3D 효과가 물리 궤적, 정지 자세, 판정 결과를 바꾸지 않는지 확인합니다.
- Sprite Atlas에서 효과가 인접 Sprite를 번지게 하지 않는지 확인합니다.
- 효과 해제와 오브젝트 재사용 후 이전 시각 상태가 남지 않는지 확인합니다.
- 공유 Material 에셋이 실행 중 변경되어 저장되지 않았는지 diff로 확인합니다.
- 효과를 추가한 뒤 SRP Batcher 적용 여부, 추가 렌더 패스, 셰이더 변형 증가를 Frame Debugger나 Profiler로 확인합니다. 성능 판단은 대상 기기 측정으로 합니다.
