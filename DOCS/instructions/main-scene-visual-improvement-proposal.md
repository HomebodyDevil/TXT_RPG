# TMP_MainScene 기반 시각적 개선안 Scene 제작

## 목적과 작업 범위

`Assets/Scenes/TMP_MainScene.unity`에 임시 배치된 기존 UI를 바탕으로, 텍스트 중심 RPG에 적합한 개선안을 실제 실행 가능한 새 Scene으로 제작한다. 문서나 정적 목업만 만드는 작업이 아니다. 기존 기능을 유지하면서 레이아웃, 정보 우선순위, 이미지, 색상, 여백과 상호작용 상태를 개선하고 원본과 비교할 수 있어야 한다.

이 문서는 구현 예정 지침이다. 새 Scene과 리소스는 아직 이 문서를 통해 생성되지 않았다. 장기 유지보수를 고려한 소규모 게임으로 취급하며 시각적 제안 하나를 완성한다. 새로운 전투·인벤토리·저장 시스템이나 범용 테마 프레임워크를 개발하지 않는다.

## 사전 확인과 현재 확인된 구성

1. `AGENTS.md`, `DOCS/README.md`와 아래 관련 문서를 읽는다.
   - `DOCS/architecture/flexible-layout-panel.md`
   - `DOCS/architecture/story-text-panel.md`
   - `DOCS/architecture/character-display-panel.md`
   - `DOCS/architecture/enemy-display-panel.md`
   - `DOCS/architecture/action-grid-panel.md`
   - `DOCS/architecture/character-status-ui.md`
   - `DOCS/architecture/quick-items-and-game-windows.md`
   - `DOCS/architecture/main-scene-default-presentation.md`
   - `DOCS/architecture/scene-transition.md`
   - `DOCS/architecture/asset-management.md`
2. Editor 연결, 컴파일 상태, 저장되지 않은 Scene·Prefab 변경과 현재 작업 파일을 확인한다. 사용자의 미저장 변경을 임의 저장하거나 폐기하지 않는다. 새 Scene의 기준이 저장본인지 현재 편집본인지 명시하고, 둘이 다르면 사용자 선택이 필요한 부분을 확인한다.
3. 저장된 Scene에는 `Main_FlexibleLayoutPanel`, `Text_FlexibleLayoutPanel`, `Character_FlexibleLayoutPanel`, `TMP_FlexibleLayoutPanel`, `StoryTextPanel`, `CharacterDisplayPanel`, `EnemyDisplayPanelDemo`, `HealthBarPanel`, `ActionGridPanel`, `GameMenuPanel` 이름이 확인된다. 이는 직렬화된 이름을 확인한 결과이지 모든 기능과 화면 표시가 정상이라는 뜻은 아니다. 실제 Hierarchy, Prefab 원본, Override, 바인딩과 Game View를 재확인한다.
4. 같은 해상도에서 원본의 초기 표시 및 메뉴가 열린 상태를 캡처한다. 문제를 확인된 동작 오류와 시각적 개선 제안으로 구분한다. 문서와 Scene이 다르면 실제 자산을 기준으로 차이를 기록한다.

| 대상 | 요구사항 |

| `DOCS/development/main-scene-visual-proposal.md` | 구현 후 실제 계층, 변경 이유, 리소스 출처, 실행 방법, 비교 이미지, 제한 사항을 기록한다. README에도 연결한다. |

원본 TMP_MainScene, AppScene의 기본 시작 대상, 기존 공용 Prefab·Style·캐릭터 콘텐츠를 시각적 실험 때문에 변경하지 않는다. 새 Scene의 인스턴스 Override 또는 전용 Prefab Variant·Style로 차이를 격리한다. 원본 전체를 재생성하지 않는다. Scene을 복사할 때 `.meta`의 GUID를 재사용하지 않는다.

## 시각적 구성 방향

아래 방향은 출발점이며 확정 디자인이 아니다. 기존 이미지와 실제 공간을 확인한 후 일관된 디자인 한 가지를 선택하고 이유를 남긴다.

- 텍스트를 주 콘텐츠로 유지한다. 넓은 화면에서는 왼쪽에 충분한 이야기 영역을 두고 오른쪽에 캐릭터·적의 시각 정보를 배치한다. 캐릭터와 적의 구분이 명확해야 하며 적이 여럿이어도 서로 또는 필수 UI를 가리지 않아야 한다.
- 빠른 아이템 영역과 메뉴 영역은 이야기 읽기를 방해하지 않는 하단 또는 별도 좁은 영역에 배치한다. 기존 메뉴 기능을 삭제하거나 작동하지 않는 장식 버튼으로 대체하지 않는다.
- 체력 정보는 캐릭터와의 관계가 명확한 위치에 둔다. 텍스트, 바, 배경의 대비를 확보한다. 기존에 없는 스탯 정보를 임의 생성하지 않는다.
- 글자 크기, 줄 간격, 내부 여백, 패널 간격, 테두리 두께, 아이콘 스타일에 일관된 기준을 적용한다. 화면 전체를 장식으로 채우지 않는다. 무채색에 제한적인 강조색을 쓰는 등 기존 아트와 어울리는 절제된 방향을 우선 검토한다.
- 배경 이미지는 본문 가독성을 우선한다. 본문 뒤에는 충분한 명암 분리 또는 중립 배경을 둔다. 캐릭터 이미지는 종횡비와 의도한 Crop을 유지하며 얼굴이나 중요한 부분이 임의로 잘리지 않게 한다.
- 좁은 화면에서는 기존 FlexibleLayout의 반응형 기능을 이용해 축·비율을 조정한다. 단순 전체 축소로 글자와 터치 영역을 줄이지 않는다. 필요한 스크롤을 허용하고 정보와 버튼에 계속 접근할 수 있게 한다.

## 재사용할 책임과 데이터 소유권

| 역할 | 작업 원칙 |
| --- | --- |
| Scene 조합 | 기존 `FlexibleLayoutPanel`과 `FlexibleLayoutItem`으로 배치하며 불필요한 신규 Layout 시스템을 만들지 않는다. |
| 패널 표시 | `Assets/TxTRPG/UI/Prefabs/`의 기존 패널을 재사용한다. Story, 캐릭터, 적, 체력, 빠른 아이템, 메뉴의 기존 API와 표시 책임을 유지한다. |
| 외형 설정 | 전용 Style·Sprite·Material에 표현 설정을 두고 게임 규칙이나 저장 상태를 넣지 않는다. |
| 런타임 상태 | 기존 세션·Presenter·초기화 경로를 사용한다. 미리보기 UI가 별도 운영 매니저나 저장 데이터를 생성하지 않는다. |
| 창과 입력 | 기존 Window 서비스와 명시적 참조를 사용한다. 모달을 마스크나 스크롤 영역에 넣어 잘리지 않게 하며 장식은 입력을 가로채지 않는다. |

배경, 콘텐츠, 전경의 기존 레이어 책임을 유지한다. `BackgroundContentLayer`는 장식이나 배경 콘텐츠가 필요한 경우 활용하되 앞쪽 콘텐츠 레이아웃을 함께 계산하도록 바꾸지 않는다. 향후 효과를 적용할 수 있도록 배경·테두리·내용물의 표현 대상을 구분하되 이번 작업에서 글리치나 고비용 셰이더 프레임워크까지 구현하지 않는다.

## 리소스 제작 및 관리

1. 기존 Sprite, 캐릭터 외형, 배경 Style, 아이콘을 조사하여 재사용 목록과 부족한 목록을 먼저 작성한다. 새 이미지는 실제 개선에 필요한 배경·패널 프레임·메뉴 아이콘 등으로 제한한다.
2. 필요한 이미지는 사용 가능한 이미지 제작 도구 또는 적절한 제작 방식으로 만든다. 외부 자료를 사용하면 출처와 재배포·상업적 사용 조건을 확인한다. 도구를 사용할 수 없다면 단순 Sprite·Tint 등 명시적인 임시 대안을 사용하고 완성 리소스로 오인시키지 않는다.
3. 리소스별 용도, 경로, 크기, 투명도, 제작 방식·출처, 라이선스, 교체 지점을 기록한다. 텍스트를 이미지에 포함하지 않는다. 늘어나는 프레임에는 적절한 9-slice를 검토한다.
4. UI 용도에 맞는 Import 설정과 모바일 메모리 비용을 검토한다. 불필요한 대형 텍스처, Read/Write, 개별 Material 복제, 매 프레임 Layout 갱신을 피한다. 성능 개선을 주장하려면 측정 근거를 제시한다.
5. 기존 Addressables 사용 경계를 유지한다. 새 리소스 전부를 무조건 Addressables로 옮기지 않는다. 비동기 로드가 필요하면 기존 Provider·수명 관리 경로를 재사용하고 해제·실패 대안을 확인한다. 선택적 장식 실패 때문에 초기화가 무한 대기해서는 안 된다.

## 실행과 미리보기 데이터

- 새 Scene도 기존 AppScene의 서비스와 콘텐츠 준비·전환 경로를 사용하여 확인한다. AppRoot나 전역 서비스를 개선안 Scene 안에 복제하지 않는다.
- 먼저 현재 Editor Play 시작 정책을 확인한다. 새 Scene을 열고 Play해도 기본 TMP_MainScene으로 이동할 수 있으므로 기존에 지원되는 콘텐츠 대상 선택·전환 경로를 사용한다. 없다면 개선안을 명시적으로 선택하는 최소한의 Editor 미리보기 경로를 마련하고 기본 시작 설정을 영구 변경하지 않는다.
- 비교를 위해 같은 캐릭터, 이야기, 적 수, 슬롯 수 등 동일 조건을 사용한다. 현재 데이터가 비어 있다면 기존 Preview 구조의 적용 가능성을 검토하여 격리된 표시 데이터를 사용한다. 실제 인벤토리에 샘플 아이템을 지급하거나 기존 저장을 덮어쓰지 않는다.
- 정상 데이터, 정상적인 빈 상태, 누락 설정과 로드 실패를 구분한다. 보기 좋은 화면을 만들기 위해 실제 오류를 숨기지 않는다. 긴 텍스트, 여러 적과 채워진 슬롯을 보여주기 위한 Preview는 운영 상태와 분리하고 활성화 방법을 명시한다.
- 로드·레이아웃 준비 후 표시되는 기존 정책을 유지한다. 전역 Fade와 패널 Fade를 임의 중복 적용하지 않는다.

## 구현 순서

1. 원본 화면과 자산 연결을 확인하고 개선할 항목 및 유지할 동작을 정리한다.
2. 간단한 배치안과 리소스 목록을 정한 뒤 새 Scene을 만든다.
3. 기존 Prefab 연결을 유지하며 새 Scene에서 레이아웃·외형을 변경한다.
4. 필요한 리소스와 전용 설정을 적용하고 기존 서비스·입력 연결을 검증한다.
5. 아래 기준으로 실제 Game View를 확인하고 겹침·잘림·입력 문제를 수정한다.
6. 새 Scene과 자산을 저장한 뒤 다시 열어서 재현성을 확인하고 비교 자료와 문서를 작성한다.

## 검증 및 완료 기준

- 원본 Scene과 공용 자산의 의도하지 않은 변경이 없는지 diff로 확인한다. 새 Scene과 리소스의 `.meta` 및 참조 누락을 확인한다.
- 최소 1920×1080, 1280×720, 2560×1080, 모바일 세로 1080×1920에서 Game View를 확인한다. 지원하지 못하는 조건은 숨기지 않고 보고한다. Safe Area와 긴 한국어·영어 문구, 확대된 글자에서도 필수 정보가 유지되어야 한다.
- Story 최신 메시지 위치·스크롤, 캐릭터 Crop, 적 0/1/여럿, 체력 표시, 빠른 슬롯 빈 상태/넘침, 메뉴와 모달 열기·닫기·탭·페이지·스크롤을 기존 지원 범위에서 확인한다.
- 마우스 클릭, 키보드·컨트롤러 포커스/취소와 터치 경로를 확인한다. 에디터의 터치 모의 확인과 실제 기기 확인을 구분한다.
- 저장 후 재진입, Play 재시작과 Scene 재로드에서 중복 서비스·이벤트 구독·리소스 누수가 발생하지 않는지 관련 경로를 확인한다. 코드 변경이 있다면 영향 범위의 테스트와 컴파일을 수행한다.
- 원본/개선안을 같은 조건으로 캡처하고 최소 기본 화면, 모달 화면, 좁은 화면의 개선 결과를 문서에 첨부한다. 정적 분석만 했다면 실행·시각 검증을 완료했다고 쓰지 않는다.

## 문서 갱신과 최종 보고

구현 완료 후 실제 제작 내용을 `DOCS/development/main-scene-visual-proposal.md`에 기록하고 `DOCS/README.md`에 연결한다. 새 주요 디렉터리·의존성이 생겼다면 `DOCS/architecture/project-structure.md`, 실행 경로가 추가되었다면 `DOCS/development/workflows.md`도 갱신한다.

최종 보고에는 새 Scene 경로, 원본 보존 여부, 핵심 시각적 변경과 이유, 새 리소스 목록, 비교 이미지, 실행 방법, 실제 수행한 검증과 미검증 항목을 포함한다. 개선안을 운영 기본 Scene으로 교체하는 작업은 이번 범위에 포함하지 않는다.

Editor 자동화를 사용할 수 있다면 자산 적용·저장·검증까지 수행한다. 임시 Tools 적용 메뉴는 AGENTS.md에 따라 허용하지만, 수동 적용이 남으면 별도의 `사용자가 수행할 적용 절차`에 전제 조건, 정확한 메뉴 전체 경로, 실행 순서, 저장 방법과 성공 확인 기준을 번호가 있는 코드 블록으로 제공한다. 코드·도구만 작성한 상태와 Scene까지 적용·검증한 상태를 구분한다.
