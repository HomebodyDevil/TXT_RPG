# 타입 기반 모달 요청과 단일 창 담당자 구현 지침

## 목적과 범위

메뉴 버튼이 모달을 직접 조작하지 않고 단일 담당자에게 타입·설정·데이터 연결 정보를 전달하여 창을 열도록 변경합니다. 가방과 시스템 메뉴에 기본 요청 구성을 적용하고 TMP_MainScene에서 실제 동작하도록 합니다.

이번 문서는 후속 구현 계획입니다. 기존 GameWindowService를 단일 담당자로 확장하며 별도 경쟁 관리자나 전역 Singleton을 만들지 않습니다. 실제 장비 시스템, 설정 항목, 버리기 및 새로운 저장 형식은 범위 밖입니다.

## 1. 단일 담당자와 개방 경로

GameWindowService를 유일한 운영 모달 열기 진입점으로 사용합니다. 이름을 유지하여 기존 Scene 참조와 직렬화 호환성을 최대한 보존합니다.

- 버튼, 단축키, 재시도, 프로그램 코드 모두 동일한 요청 경로를 사용합니다.
- 호출자는 host.SetVisible(true), page.Show(), 직접 Instantiate 또는 SetActive로 모달을 열지 않습니다.
- Host와 Page는 서비스가 호출하는 표시 구현입니다. 가능한 범위에서 표시 API 접근을 제한하고 실제 우회 호출을 제거합니다.
- Unity Inspector로 객체를 활성화하는 것까지 언어 수준에서 금지한다고 주장하지 않습니다. 런타임 호출 경계와 테스트로 규칙을 유지합니다.
- 서비스는 요청 검증, 본문 선택, 설정 적용, 데이터 준비, 표시, 입력·포커스, 취소·닫기·오류·재시도를 소유합니다.
- 아이템 소유권과 효과 실행은 서비스에 넣지 않습니다.
- 기존 OpenAsync(string, ...)가 필요하면 기본 요청을 만드는 호환 wrapper로 남깁니다. 별도 구형 동작 경로를 유지하지 않습니다.

## 2. 타입과 요청 구성

신규 제안 타입은 ModalOpenRequest와 ModalContentKind입니다. 실제 명칭은 기존 프로젝트 관례에 맞출 수 있습니다.

| 값 | 의미 |
| --- | --- |
| ItemGrid | 아이템 표현 모델을 Slot 그리드로 표시합니다. SlotWithGrid보다 목적이 명확한 명칭입니다. |
| CustomContent | 시스템 설정 등 일반 UI 본문을 표시합니다. 이번 기본 시스템 본문은 비어 있습니다. |

페이지 여부는 본문 타입과 별개인 VerticalScroll/Paged 설정으로 둡니다. ItemGrid와 ShowSlots=false처럼 모순된 bool 조합은 만들지 않습니다.

요청에는 다음 내용을 포함합니다.

- 안정적인 WindowId: 기존 inventory, system 값을 유지합니다.
- ContentKind와 현지화 가능한 제목입니다.
- 해당 타입에 유효한 표시 설정입니다.
- 데이터 공급자 키 또는 주입된 공급 계약입니다.
- 필요한 카테고리와 최초 카테고리·페이지 선택 정보입니다.
- 창 종료 후 포커스를 돌려줄 호출자 정보입니다.

타입별 요청 설정을 명확하게 구분합니다. 공통 Dictionary<string, object>나 숫자 인덱스만으로 데이터를 넘기지 않습니다. 요청 생성 후 설정을 복사하여 외부 변경이 진행 중인 준비를 바꾸지 못하게 합니다.

Inspector용 메뉴 설정에는 직렬화 가능한 요청 정의를 두고, 런타임 Application Binder/Factory가 공급자를 연결하여 완전한 요청을 만듭니다. UI 정의 자산이 플레이어 상태나 Scene 객체를 영구 소유하지 않게 합니다.

## 3. 데이터 공급자는 기존 관리 상태를 이용합니다

- ItemGrid 요청은 UI용 목록·카테고리·변경 알림을 제공하는 명확한 계약을 사용합니다. 예시 이름은 IModalItemSource입니다.
- Application의 가방 Adapter가 기존 InventoryState와 ItemCatalog를 조합하여 UI 표현을 제공합니다.
- UI 또는 GameWindowService에서 PlayerState를 생성하거나 아이템 목록의 별도 원본을 유지하지 않습니다.
- 소비품·장비는 우선 카테고리 ID로 분류합니다. 아직 독립 관리자가 없으면 이를 새로 만들지 않습니다.
- 추후 장비 등 별도 관리자가 생기면 Adapter를 통해 같은 공급 계약에 연결할 수 있게 합니다. 서비스가 구체적인 관리자 클래스를 참조하지 않습니다.
- 슬롯에는 안정적인 항목 ID, 이름, 수량, 아이콘 식별과 실행 가능 상태를 전달합니다. 페이지 내 인덱스를 아이템 ID로 사용하지 않습니다.
- 공급자를 통한 목록 조회는 표시를 위한 작업이며 소유 데이터의 재배열·삭제가 아닙니다.
- 사용·퀵 슬롯 등록은 기존 IActionMenuProvider/IActionCommandExecutor와 Application 서비스 경로를 유지합니다.
- 공급자 교체·창 종료 시 이벤트와 자산 Lease를 해제합니다. 서비스가 공급자 자체를 생성했는지 빌려 쓰는지에 따라 Dispose 책임을 구분합니다.

## 4. 카테고리와 페이지 구성

기존 GridContentLayoutSettings와 카테고리 계산을 재사용합니다. 범용 UI 계약이 Application을 역참조하지 않게 필요한 표시 DTO만 적절한 공통 경계로 옮기거나 Adapter를 둡니다. 무관한 클래스 전체를 이동하지 않습니다.

- 카테고리 필터 → 안정적인 정렬 → 페이지 분할 → 슬롯 바인딩 순서를 지킵니다.
- 전체, 소비품, 기타를 기존 기본값으로 유지합니다. 장비 탭이 필요하면 분류만 추가하고 장착 기능은 추가하지 않습니다.
- 카테고리별로 결과가 여러 페이지가 될 수 있습니다. 같은 데이터를 카테고리마다 복제하지 않습니다.
- Paged에서만 SlotsPerPage를 적용합니다. 개발자가 1 이상으로 지정할 수 있어야 합니다.
- VerticalScroll은 해당 카테고리 전체 결과를 표시하며 페이지당 개수 제한을 적용하지 않습니다.
- 슬롯 크기·간격·Padding·열 수와 Exact/Adaptive 정책은 기존 설정을 사용합니다.
- 빈 칸 표시 정책과 실제 인벤토리 용량을 혼동하지 않습니다.

### 특정 페이지 버튼

GoToPage API만 제공하는 것으로 완료하지 않습니다. 실제 사용자 버튼으로 임의의 페이지에 갈 수 있어야 합니다.

- 현재 페이지 번호가 구분되는 번호 버튼과 이전·다음 버튼을 제공합니다.
- 페이지가 적으면 전체 번호를, 많으면 제한된 번호 구간과 첫/끝·구간 이동 또는 페이지 선택 패널을 제공합니다.
- 생략된 번호도 몇 번의 명시적 조작으로 선택 가능해야 합니다. 버튼을 페이지 수만큼 무제한 생성하지 않습니다.
- 표시 번호는 1부터, 내부 인덱스는 0부터 사용합니다.
- 결과 0개도 논리적 1페이지이며 이동은 비활성화합니다.
- 카테고리 변경 시 기본적으로 1페이지·상단으로 이동합니다.
- 수량 변경은 선택 ID와 위치를 가능한 한 유지하고, 페이지가 줄면 마지막 유효 페이지로 보정합니다.
- 페이지·탭 변경 전 컨텍스트 메뉴를 닫습니다.
- 고정 칸 수와 열 수가 화면에 들어가지 않는 경우 설정 오류를 알려주고, 무단 누락이나 자동 모드 변경으로 숨기지 않습니다.

## 5. 기본 요청과 대체 설정

유효한 사용자 설정은 보존합니다. 미지정 값만 다음 제안 기본값으로 채웁니다.

| 메뉴 | 기본 요청 |
| --- | --- |
| Bag/inventory | ItemGrid + Paged + 페이지당 12칸 + 최대 4열의 반응형 배치 + 기존 카테고리 + 실제 가방 공급자입니다. |
| System/system | CustomContent + 제목/닫기/빈 ContentRoot이며 아이템 공급자와 페이지 버튼을 요구하지 않습니다. |

Bag의 Paged는 새 기본 정의의 제안입니다. 기존 Scene에서 VerticalScroll을 명시했다면 자동으로 덮어쓰지 않습니다. 두 모드를 Inspector에서 선택하고 실제 동작을 확인할 수 있게 합니다.

설정 우선순위는 요청의 유효한 설정 → 메뉴별 개발자 기본 정의 → 코드의 안전한 최종 기본값입니다. 설정 원본을 런타임에서 직접 수정하지 않습니다.

- 표시 설정이 없으면 기본값으로 창을 구성합니다.
- 요청 타입이 알 수 없거나 필수 데이터 공급자가 없으면 잘못된 기본 창으로 바꾸지 않고 안전한 오류 상태를 표시합니다.
- 빈 인벤토리는 정상 빈 가방이며 테스트 아이템을 생성하지 않습니다.
- 세션·카탈로그·필수 UI 참조 오류는 기본 데이터로 덮어 숨기지 않습니다.
- 시스템은 실제 옵션을 추가하지 않고 정상적인 빈 모달을 제공합니다.
- 오류 문구는 읽을 수 있는 공통 영역에 표시하고 내부 예외 원문은 개발 진단으로 분리합니다.

## 6. 준비·취소·재시도 수명

기본 흐름은 요청 검증 → 입력 차단 및 로딩 표시 → 본문 선택 → 설정 해석 → 공급 데이터 준비 → 레이아웃 확정 → 본문 표시 및 포커스 설정입니다.

- 기존 latest-request-wins 정책을 유지합니다.
- 새 요청은 이전 준비를 취소하고 늦게 완료된 결과가 현재 창을 덮어쓰지 못하게 합니다.
- 재시도는 마지막 ID만이 아니라 타입·설정·공급자 연결을 포함한 원래 논리 요청을 재실행합니다. 재시도 시 취소된 토큰을 재사용하지 않습니다.
- 공급자 수명이 끝났다면 유효성을 다시 확인하여 재연결 또는 오류로 처리합니다.
- 닫기는 준비 작업과 소유 리소스를 정리하고 입력 차단을 해제합니다.
- 같은 요청 반복 클릭으로 페이지·구독·모달이 중복 생성되지 않아야 합니다.
- 메뉴 호출자와 최초 포커스를 보존합니다. 빈 시스템 창은 닫기 버튼에 초점을 둡니다.
- 가방 내 컨텍스트 취소가 모달까지 한 번에 닫지 않도록 가장 안쪽 UI부터 Cancel을 처리합니다.

## 7. 적용과 호환성

1. 실제 OpenAsync, Show, SetVisible, 직접 활성화, UnityEvent 호출자를 조사합니다.
2. 기존 GameWindowService를 확장하고 요청 검증과 타입별 Adapter를 구현합니다.
3. 기존 메뉴 바인딩과 재시도를 같은 요청 경로로 이전합니다.
4. 가방 공급자와 시스템 기본 본문을 연결하고 번호 페이지 버튼을 적용합니다.
5. TMP_MainScene의 기존 메뉴와 모달 인스턴스를 직접 수정·저장·검증합니다.

새 영구 Tools 메뉴나 전체 Scene Rebuild를 추가하지 않습니다. Unity 아키텍처 지침에 따라 작고 명확한 책임 분리를 유지합니다. 기존 GUID, PageId, 이미지, 메뉴 배치, 사용자 설정과 저장 데이터를 보존합니다. 생성형 자산은 필요한 원본 코드만 일관되게 수정합니다.

“담당자를 통해서만 연다”는 규칙을 관련 아키텍처 문서와 호출 경계 테스트에 기록합니다. 기존 모달 개방 호출의 미이전 목록을 남기지 말고 모두 확인합니다. 그리드 내부 컨텍스트 메뉴는 이번 중앙화 대상인 메뉴 모달과 구분합니다.

## 8. 검증과 완료 기준

- 실제 Bag/System 버튼이 타입과 설정을 가진 요청을 같은 서비스에 전달하는지 검증합니다.
- 잘못된 타입·필수 공급자 누락·설정 누락과 기본값 적용을 각각 검사합니다.
- 가방 데이터를 기존 관리 상태에서 가져오고 필터·페이지 이동이 이를 변경하지 않는지 확인합니다.
- 0, 1, K, K+1 및 여러 카테고리·다수 페이지를 검사합니다.
- 실제 번호 버튼으로 중간 페이지와 마지막 페이지에 접근할 수 있는지 확인합니다.
- Paged/VerticalScroll과 런타임 설정 변경, 마지막 페이지 항목 제거를 검사합니다.
- 느린 공급자·아이콘, 연속 메뉴 클릭·재시도·닫기에서 오래된 결과가 표시되지 않는지 확인합니다.
- 시스템은 빈 모달만 표시하고 불필요한 아이템 초기화를 수행하지 않는지 확인합니다.
- 기존 아이템 명령, 입력 차단, 터치·마우스·키보드·게임패드 탐색과 포커스를 회귀 검증합니다.
- 좁은 화면·긴 번역에서 탭·페이지 버튼·닫기와 오류가 읽히는지 확인합니다.
- 저장 후 Prefab/Scene 재로드와 AppScene 경유 실제 Play Mode 검증을 수행합니다.
- 사용자 저장 데이터는 건드리지 않고 필요하면 격리된 테스트 세션을 사용합니다.
